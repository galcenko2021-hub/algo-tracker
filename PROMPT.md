# Задача: реализуй проект `algo-tracker`

Ты — старший full-stack инженер. Построй с нуля законченный портфолио-проект и доведи его до рабочего состояния: код, тесты, Docker, CI, документация. Работай автономно, по этапам (раздел 12), проверяй каждый этап запуском тестов и линтеров, не сообщай «готово», пока это не подтверждено командами.

## 1. Что за проект

**algo-tracker** — веб-трекер решённых алгоритмических задач.
Карточка в портфолио: «Веб-трекер решённых алгоритмических задач: теплокарта активности, разбор по темам и напоминания о повторении.»
Стек (фиксирован): **TypeScript, React, FastAPI, PostgreSQL.**

Пользователь (студент, готовится к алгоритмическим интервью и олимпиадным задачам) делает следующее:
- заносит решённые задачи вручную или импортирует их из Codeforces;
- видит теплокарту активности и серии (streak);
- видит разбор по темам (теги) и слабые места;
- получает напоминания о повторении задач по алгоритму интервального повторения (SM-2);
- получает рекомендации, какую задачу решать дальше.

Интерфейс на русском языке. Код, имена, комментарии, сообщения коммитов — на английском. README и DECISIONS.md — на русском.

## 5. Модель данных (PostgreSQL)

Все времена хранить в UTC (`timestamptz`). Агрегации по дням делать в часовом поясе пользователя.

- `users`: `id`, `email` (unique, нижний регистр), `password_hash`, `cf_handle` (nullable), `timezone` (по умолчанию `Europe/Moscow`, валидировать по IANA), `created_at`.
- `problems`: `id`, `platform` (enum: `codeforces`, `leetcode`, `yandex`, `other`), `external_id` (для CF: `"{contestId}{index}"`, например `"1700A"`), `title`, `url`, `rating` (int, nullable), `created_at`. `UNIQUE(platform, external_id)`. Для `other` без `external_id` генерируй стабильный id из нормализованного названия.
- `tags` (`id`, `name` unique) и `problem_tags` (`problem_id`, `tag_id`).
- `solves`: `id`, `user_id`, `problem_id`, `solved_at`, `source` (enum: `manual`, `codeforces`), `time_spent_min` (nullable), `notes` (nullable, до 2000 символов). `UNIQUE(user_id, problem_id)`.
- `attempt_stats` (для ML): `user_id`, `problem_id`, `tries` (int), `solved` (bool), `first_attempt_at`. `UNIQUE(user_id, problem_id)`. Заполняется только импортом с Codeforces.
- `review_cards`: `id`, `user_id`, `problem_id`, `ease` (float, старт 2.5), `interval_days` (int), `repetitions` (int), `lapses` (int), `due_date` (date), `last_reviewed_at`. `UNIQUE(user_id, problem_id)`. Карточка создаётся автоматически при добавлении решения (первое повторение через 1 день).
- `review_log`: `id`, `card_id`, `reviewed_at`, `quality` (0–5), `interval_after`, `ease_after`.
- `cf_catalog`: каталог задач Codeforces для рекомендаций: `external_id`, `title`, `url`, `rating`, `tags` (массив), `solved_count`, `fetched_at`. Обновляется по требованию, TTL 24 часа.

Индексы: `solves(user_id, solved_at)`, `review_cards(user_id, due_date)`, `problem_tags(tag_id)`.

Миграции только через Alembic. Первая миграция создаёт всю схему.

## 6. REST API (префикс `/api`, OpenAPI доступен на `/docs`)

**Аутентификация**
- `POST /auth/register {email, password}` → 201. Пароль минимум 8 символов. Дублирующий email → 409.
- `POST /auth/login {email, password}` → access-токен (JWT, 15 минут) в теле ответа + refresh-токен (JWT, 14 дней) в cookie `httpOnly`, `SameSite=Lax`, `Secure` вне dev-режима.
- `POST /auth/refresh` → новый access по refresh-cookie. `POST /auth/logout` → очищает cookie.
- Лимит запросов: не более 10 в минуту на IP для `/auth/*`.
- Остальные эндпоинты требуют заголовок `Authorization: Bearer ...`. Данные строго изолированы по пользователям (проверь тестом: пользователь A не видит и не меняет данные B).

**Профиль**
- `GET /me`, `PATCH /me {cf_handle?, timezone?}`.

**Решения**
- `POST /solves {platform, external_id?, title, url?, rating?, tags[], solved_at?, time_spent_min?, notes?}` — создаёт задачу в `problems`, если её нет, затем решение и карточку повторения. Повторное добавление той же задачи → 409.
- `GET /solves?from&to&tag&platform&q&page&page_size` → пагинация, сортировка по `solved_at` по убыванию.
- `PATCH /solves/{id}`, `DELETE /solves/{id}` (удаление решения удаляет и карточку повторения).
- `GET /tags?q=` — автодополнение тегов пользователя.

**Статистика**
- `GET /stats/summary` → `{total, last_7_days, last_30_days, current_streak, longest_streak}`.
- `GET /stats/heatmap?from&to` → `[{date, count}]` за период (по умолчанию последние 365 дней), по локальным датам пользователя.
- `GET /stats/topics` → по каждому тегу: `solved`, `share`, `avg_rating`, `last_solved_at`, `avg_review_quality`, `weakness` (формула в разделе 8).
- Серия: подряд идущие локальные дни с ≥1 решением. Если сегодня решений ещё нет, серия не обрывается до конца сегодняшнего дня (считай от вчера).

**Повторения**
- `GET /reviews/due` → карточки на сегодня и раньше (данные задачи, заметка) + счётчик.
- `POST /reviews/{card_id}/answer {quality}` → применяет SM-2, пишет `review_log`, возвращает новый интервал и дату.
- `GET /reviews/upcoming?days=14` → количество карточек по дням.

**Импорт**
- `POST /import/codeforces {handle?}` — если `handle` не передан, берётся из профиля. Возвращает `{imported, skipped, attempts_recorded}`. Операция идемпотентна: повторный запуск ничего не дублирует.

**Рекомендации**
- `GET /recommendations?limit=5` → список `{problem, score, reason, predicted_solve_prob?}` (раздел 8).

## 7. Интеграция с Codeforces

Используй только публичный API: https://codeforces.com/api/

- `GET /user.status?handle={handle}` → `{"status": "OK", "result": [Submission, ...]}`.
  Поля Submission, которые тебе нужны: `id`, `contestId` (может отсутствовать), `creationTimeSeconds`, `problem` = `{contestId, index, name, type, rating?, tags[]}`, `verdict` (`"OK"`, `"WRONG_ANSWER"`, ...).
- `GET /problemset.problems` → `{"status": "OK", "result": {"problems": [...], "problemStatistics": [{contestId, index, solvedCount}, ...]}}`.
- Ошибка: `{"status": "FAILED", "comment": "handle: User with handle X not found"}` → верни пользователю понятное сообщение (404 для неизвестного хэндла, 502 для недоступности API, 429 при превышении лимита).
- Лимит Codeforces: не чаще одного запроса в 2 секунды. Реализуй троттлинг на уровне клиента и таймауты (connect 5 с, read 30 с), максимум 2 повтора с экспоненциальной паузой.
- Ссылка на задачу: `https://codeforces.com/problemset/problem/{contestId}/{index}`. Задачи из gym (`contestId >= 100000`) пропускай.

**Правила импорта**
1. Из всех посылок сформируй по задаче: число попыток `tries`, факт решения (`solved` = есть посылка с `verdict == "OK"`), время первой попытки.
2. Запиши `attempt_stats` для всех задач (и решённых, и нет).
3. Для решённых задач создай `problems` (если нет), теги и `solves` с `solved_at` = время **первой** OK-посылки и `source = codeforces`, плюс карточки повторения. Если решение уже есть (в том числе ручное), пропусти.
4. Для импортированных старых решений не создавай просроченную лавину карточек: ставь `due_date` равным дате решения + 1 день, но не раньше сегодняшней, и распределяй первые повторения равномерно, не более 10 новых карточек в день.
5. Всё в одной транзакции, массовая вставка (без запроса на каждую строку).

## 8. Алгоритмы (чистая логика, без БД, полностью покрыта тестами)

### 8.1 Планировщик повторений (SM-2)
Функция `schedule(card_state, quality, today) -> card_state`.
- `quality` ∈ {0..5}. В интерфейсе четыре кнопки: «Снова» → 1, «Трудно» → 3, «Хорошо» → 4, «Легко» → 5.
- Если `quality < 3`: `repetitions = 0`, `interval = 1`, `lapses += 1`, `ease` не меняется.
- Иначе: `repetitions == 0` → `interval = 1`; `repetitions == 1` → `interval = 6`; иначе `interval = round(interval * ease)`; затем `repetitions += 1`.
- `ease = max(1.3, ease + 0.1 - (5 - q) * (0.08 + (5 - q) * 0.02))` (применяется при `q >= 3`).
- `due_date = today + interval` дней.
- Спрячь реализацию за интерфейсом `Scheduler`, чтобы позже можно было заменить на FSRS.
- Тесты: таблица ожидаемых значений для последовательностей ответов, границы `ease`, сброс при «Снова».

### 8.2 Слабость темы (weakness)
Для тега `t`, у пользователя с `N` решениями всего:
- `coverage_t = solved_t / N`
- `quality_t` = средняя оценка повторений по задачам этого тега (с байесовским сглаживанием к априорному значению 3.5 с весом 3 наблюдения; если повторений нет, используется априор).
- `weakness_t = 0.5 * (1 - min(1, coverage_t / 0.15)) + 0.5 * (1 - quality_t / 5)` → число от 0 до 1.
- Всё в `services/stats.py`, с тестами.

### 8.3 Рекомендации, уровень 1 (эвристика, обязателен)
1. Оцени уровень пользователя: медиана рейтингов последних 20 решённых задач с рейтингом (если их нет, 800). Округли до 100.
2. Кандидаты: задачи из `cf_catalog`, не решённые пользователем, с рейтингом в `[level - 100, level + 200]`.
3. Оценка кандидата: `score = Σ_t∈tags weakness_t / sqrt(len(tags)) + 0.2 * closeness`, где `closeness = 1 - |rating - (level + 100)| / 300`.
4. Верни топ-N, по каждой задаче — человекочитаемое объяснение, например: «Слабая тема: dp (решено 3, средняя оценка повторений 2.8). Рейтинг 1200 близок к вашему уровню 1100».
5. Реализация за интерфейсом `Recommender`.

### 8.4 Рекомендации, уровень 2 (ML, обязателен при достаточных данных)
Обучай **отдельную модель на пользователя** на его `attempt_stats` (после импорта с Codeforces):
- Метка: `solved` (1/0). Признаки: `rating - level`, мульти-hot по тегам (словарь из `cf_catalog`), `log(1 + solved_count)` как прокси популярности.
- Модель: `LogisticRegression` с L2-регуляризацией, подбор `C` по времени-ориентированной кросс-валидации. Разбиение для оценки **по времени** (первые 80% по `first_attempt_at` в обучение, последние 20% в тест), без перемешивания.
- Минимум данных: ≥ 100 задач с попытками, из них ≥ 20 положительных и ≥ 20 отрицательных. Иначе используй уровень 1 (fallback) и сообщи об этом в ответе API.
- Использование: для кандидатов считай `p_solve`. Выбирай задачи с `p_solve` около 0.6 («зона ближайшего развития») и повышай приоритет для слабых тем: `score = weakness_sum + 1 - |p_solve - 0.6| / 0.6`.
- Скрипт `scripts/eval_recommender.py`: печатает ROC-AUC, log-loss на отложенной выборке и сравнивает с базовой моделью «только `rating - level`». Результат (на синтетических данных, явно помеченных как синтетические) положи в README.
- В README честно опиши ограничения: смещение выбора (пользователь сам выбирает, что пробовать), «не решил» ≠ «не смог бы решить», мало данных на одного человека. Это эвристическая рекомендательная система, а не доказательство навыка.

## 9. Frontend

Страницы (React Router, защищённые маршруты, токен хранится в памяти, обновляется через `/auth/refresh`):
- `/login`, `/register`.
- `/` **Дашборд**: карточки сводки (всего, серия, за 7/30 дней), баннер «Сегодня к повторению: N», теплокарта.
- **Теплокарта**: SVG, 53 недели × 7 дней в стиле GitHub, 5 уровней интенсивности, подсказка при наведении («12 окт 2026: 3 задачи»), начало недели понедельник, переключатель периода, доступная: у ячеек `aria-label`, фокус с клавиатуры, палитра, различимая при дальтонизме.
- `/solves`: таблица с фильтрами (теги, платформа, период, поиск), пагинация, модальное окно добавления/редактирования (чипы тегов с автодополнением, валидация формы).
- `/topics`: столбчатая диаграмма и радар по темам, таблица с сортировкой по слабости, ссылка на фильтр решений по теме.
- `/reviews`: режим повторения по одной карточке, показывает название, ссылку и заметку; четыре кнопки с горячими клавишами `1–4`; на кнопках видно, через сколько дней карточка вернётся; в конце экран «Готово на сегодня».
- `/recommendations`: карточки с рейтингом, тегами, объяснением и меткой «ML» или «эвристика»; кнопка «Открыть на Codeforces».
- `/settings`: CF-хэндл, часовой пояс, кнопка «Импортировать с Codeforces» с результатом, экспорт данных в JSON.

Дизайн: минималистичный тёмный интерфейс в духе dev-инструментов (светлая тема тоже, с учётом `prefers-color-scheme`), моноширинный шрифт для чисел и заголовков карточек, один акцентный цвет, адаптивная вёрстка (работает на телефоне), состояния загрузки, пустые состояния и понятные сообщения об ошибках. Все запросы через TanStack Query, типы ответов API описаны в `src/api/types.ts`.

## 10. Тесты и качество

**Backend (pytest, цель: покрытие `app/services` и `app/api` ≥ 85%)**
- Юнит-тесты: SM-2, серия и теплокарта (смена суток по часовому поясу, переход через границу месяца, пустые данные), weakness, эвристика рекомендаций, ML-ветка (на синтетических данных с фиксированным seed, проверка fallback при нехватке данных).
- Интеграционные тесты API на реальном PostgreSQL (в CI — `services: postgres`, локально — через docker-compose или `testcontainers`): регистрация, вход, refresh, изоляция данных между пользователями, CRUD решений, 409 на дубликаты, фильтры, пагинация, ответ на повторение.
- Импорт: идемпотентность (двойной запуск), только `OK` попадает в решения, `attempt_stats` включает неудачные попытки, неизвестный хэндл → 404, ошибка API → 502. Все ответы Codeforces мокаются фикстурами.

**Frontend (Vitest + RTL)**: компонент теплокарты (уровни интенсивности, доступность), форма добавления решения (валидация), экран повторения (горячие клавиши, переход к следующей карточке), защищённый маршрут.
