# DECISIONS

Неочевидные решения, принятые по ходу работы.

1. **Синхронный SQLAlchemy.** Нагрузка небольшая, sync-стиль проще тестировать и отлаживать; FastAPI запускает sync-эндпоинты в пуле потоков. Асинхронность не даёт здесь выигрыша.
2. **`uv` + `pyproject.toml` + `uv.lock`.** `uv` установлен через `pip --user`; Python 3.12 поставлен самим `uv`, т.к. в системе только 3.14.
3. **Тестовая БД.** В окружении разработки нет Docker, поэтому интеграционные тесты идут на реальном PostgreSQL 16 по `TEST_DATABASE_URL` (локально — встроенный PG из пакета `pgserver`, в CI — `services: postgres`). SQLite не используется.
4. **Rate limit через `slowapi`.** 10 запросов/мин на IP для `/auth/*`. В тестах лимитер включается только в специальном тесте, иначе остальные тесты упёрлись бы в лимит.
5. **Refresh-токен stateless.** Отзыв при logout невозможен (cookie очищается, но токен остаётся валидным до истечения). Компромисс описан в README.
6. **OpenAPI на `/api/docs`**, а не `/docs`: так документация доступна и через nginx-прокси (`/api` → backend), без отдельного маршрута. Схема — `/api/openapi.json`.
7. **Общие задачи (`problems`) не перезаписываются.** Таблица `problems` общая по ТЗ (`UNIQUE(platform, external_id)`). Если задача уже есть, её название/рейтинг/теги из запроса игнорируются, чтобы один пользователь не менял то, что видит другой. Метаданные задачи через `PATCH /solves/{id}` можно менять только пока задачей не владеет никто, кроме автора (иначе 403); дату, время и заметку — всегда.
8. **Первое повторение** = `max(локальная дата решения + 1 день, сегодня)`. Для свежего решения это «завтра», для задним числом внесённого — «сегодня», чтобы не создавать просрочку.
9. **Фильтры `from`/`to` в `/solves`** — локальные даты пользователя, обе границы включительно. Несколько `tag` = логическое И.
10. **URL задач** принимаются только `http(s)` (защита от `javascript:` в ссылках на фронтенде). Для Codeforces URL строится из `external_id`, если не передан.
11. **Группировка по локальным дням — в Python (`zoneinfo`), не `AT TIME ZONE` в SQL.** Результат не зависит от tz-базы сервера PostgreSQL (в встроенном PG из `pgserver` её нет), правила часовых поясов живут в одном месте (`tzdata` из зависимостей). История пользователя — тысячи строк, выбирается один столбец `solved_at`.
12. **SM-2: интервал считается по «старому» ease** (до учёта текущего ответа), в порядке, указанном в ТЗ. Округление — half-up (`floor(x + 0.5)`), а не банковское `round()`, чтобы поведение не зависело от чётности. Следствие: при одном и том же состоянии кнопки «Трудно/Хорошо/Легко» дают одинаковый ближайший интервал, а различие накапливается через `ease` в следующих повторениях — это свойство SM-2, на кнопках честно показываются реальные значения.
13. **Импорт создаёт `problems` и для нерешённых задач** — `attempt_stats` ссылается на `problems` внешним ключом, а ML-ветке нужны именно неудачные попытки. В `solves` попадают только задачи с `OK`.
14. **`attempts_recorded` = число новых или изменившихся строк `attempt_stats`.** При повторном запуске без новых посылок это 0 — так идемпотентность видна прямо в ответе; если появились новые посылки, счётчики обновляются (upsert).
15. **Лимит 10 новых карточек в день при импорте** учитывает уже существующие «новые» карточки (`repetitions = 0`) на эти дни; старые решения получают первые повторения по очереди, начиная с самых давних.
16. **Троттлинг Codeforces — один общий `Throttle` на процесс** (потокобезопасный), чтобы параллельные запросы пользователей не нарушали лимит в 1 запрос / 2 с. Повторы (до 2) с паузой 1 с и 2 с — только для сетевых ошибок, 5xx, 429 и «call limit exceeded».
17. **Каталог `cf_catalog` обновляется лениво** (`ensure_catalog`, TTL 24 ч). Если Codeforces недоступен, а старый каталог есть, используется он.
